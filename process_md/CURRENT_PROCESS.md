# Current Process (Playwright Extractor)

This document describes the current end-to-end workflow implemented in this repo, including:

- The orchestration entrypoints
- The **CA Match → Extract Reconciliation → RAAS+ → Match Statement** chaining
- What “RAAS+ processing” does (Excel → JSON → reconcile → Excel)
- How the “Match Statement” step decides what to process (sheet-driven “match type” logic)

---

## 1) Entrypoints and Orchestration

### Entrypoint scripts

- `run_playwright.py` (repo root)
  - Thin wrapper that calls `playwright_scripts.run_playwright.main()`.
- `playwright_scripts/run_playwright.py`
  - The real CLI entrypoint and “runner” orchestrator.

### Runner overview

`PlaywrightRunner` in `playwright_scripts/run_playwright.py` is the top-level orchestrator.

Inputs:

- CLI args or `.env`:
  - `accountName` / `--account`
  - `--date` (defaults to one month ago)
  - `--amount` (defaults to `100.00`)
  - `--headless` (also influenced by `HEADLESS_MODE=true/false`)
  - `--pingback-url` (optional callbacks)
  - `--webhook-url` (optional logging webhooks)
  - `--skip-ca-match`, `--skip-extract`, `--skip-match` (skip flags)

Outputs / artifacts (high level):

- `playwright_runner.log` (orchestrator log)
- Downloaded Excel files in `Downloads/` (via `helper_playwright.paths.get_downloads_dir()`)
- JSON exports in `Downloads/json_output/`
- Matching results Excel in `matching_results/` (auto-generated by RAAS+ unless overridden)
- Run logs in `logs/runs/` (notably from Match Statement and RAAS+)
- Optional: `failed_entries.xlsx` (produced by Match Statement if anything can’t be matched)

### End-to-end flow (chained)

The workflow is designed to be chained automatically:

1. **CA Match Process** (Playwright automation)
2. **Extract Reconciliation Statement** (Playwright automation)
3. **RAAS+** (local processing: Excel → JSON → reconciliation → Excel)
4. **Match Statement** (Playwright automation to apply matches back into the web app)

In code, the chaining looks like:

`process_bank_transactions()` → calls Extract → calls RAAS+ → calls Match Statement

## 2) Step 1 — CA Match Process (Playwright)

Primary module:

- `playwright_scripts/CA_Match_Process_Optimized.py`

Entry call:

- `process_bank_transactions(playwright, accountName, date, amount, ...)`

What it does (high-level):

- Launches Chromium and logs into the target site.
- Navigates to **Process Bank Records**.
- Runs an auto-match + manual-matching flow in the UI (implementation is in the module’s methods).
- Downloads the resulting bank transactions Excel file.
- Reads/returns records from the downloaded file.

Chaining behavior:

- After CA Match completes, it calls:
  - `ExtractReconcileStatement.extract_reconciliation_statements(..., save_path=<downloaded_bank_excel>)`

Key notes:

- Uses `accept_downloads=True` Playwright context and `get_downloads_dir()` to decide where downloads land.
- Sends optional `pingback_url` status updates.
- Attempts to email a status reply via `helper_playwright.email_reply.reply_to_trigger_email(...)`.

## 3) Step 2 — Extract Reconciliation Statement (Playwright)

Primary module:

- `playwright_scripts/ExtractReconcileStatement_Optimized.py`

Entry call:

- `extract_reconciliation_statements(playwright, accountName, date, amount, save_path=<bank_excel>, ...)`

What it does (high-level):

- Launches Chromium and logs into the target site.
- Navigates the UI to produce/export reconciliation-related data.
- Exports a reconciliation Excel file (reconciliation statements).
- Loads the exported Excel into a DataFrame (via `helper_playwright.functions.safe_read_excel`).

Chaining behavior:

- At the end of extraction it calls RAAS+:
  - `RaasPlus.run_RaasPlus(playwright, save_path=<bank_excel>, reconciliation_save_path=<recon_excel>, ...)`

Key notes:

- Centralized `.log()` supports optional webhook posting (`--webhook-url`).
- Sends optional `pingback_url` status updates.
- Attempts to email a status reply via `reply_to_trigger_email(...)`.

## 4) Step 3 — RAAS+ Processing (Local: Excel → JSON → Reconcile → Excel)

Primary module:

- `playwright_scripts/RaasPlus.py`

RAAS+ here is the “reconciliation engine” step: it converts the two extracted Excels into JSON, runs reconciliation logic, and produces a match-result Excel file.

### 4.1 Excel → JSON export

Code path:

- `Raas_Plus/convert_with_xlwings.py`
  - `convert_two_excels_to_json(company_statement, bank_statement, output_dir)`
  - Internally calls `convert_excel_to_json(...)` twice.

Runtime output location:

- `Downloads/json_output/` (created if missing)

Outputs:

- `company_json` path (JSON representation of reconciliation statements)
- `bank_json` path (JSON representation of bank transactions)

The RAAS+ runner verifies both JSON files exist before continuing.

### 4.2 Reconciliation engine → match-result Excel

Code path:

- `Raas_Plus/unified_reconciliation.py`
  - `reconcile_unified(bank_json_path, company_json_path, out_xlsx, ..., bank_name, ...) -> excel_path`

Important behavior:

- If `out_xlsx` is `""`, the engine auto-generates an output file under `matching_results/` (typically timestamped and bank-coded).
- The function also creates a per-run log under `logs/runs/` (tee + file logging).
- “Bank name” is derived from `accountName` (e.g., `CIM02`, `MBB02`) and passed into the engine as `bank_name` to gate bank-specific logic.

Outputs:

- `excel_path`: the path to the generated match-result Excel file that drives the next step.

### 4.3 RAAS+ → Match Statement chaining

After `reconcile_unified(...)` returns `excel_path`, RAAS+ calls:

- `playwright_scripts/MatchStatement_Optimized.run_matching_process(playwright, matchresultpath=excel_path, ...)`

## 5) Step 4 — Match Statement Process (Playwright “apply matches”)

Primary module:

- `playwright_scripts/MatchStatement_Optimized.py`

This step reads the RAAS+ output Excel and applies those matches back into the web UI (Acumatica).

### 5.1 Inputs

- `match_result_path`: the RAAS+ output Excel (from `reconcile_unified`)
- `account_name`: typically from `.env` (`accountName`) or the runner arg
- Site credentials + URL from `.env` / args:
  - `WEBSITE_URL`, `WEBSITE_USERNAME`, `PASSWORD`
- Optional callbacks:
  - `pingback_url` (status)
  - `webhook_url` (log forwarding)

### 5.2 Outputs

- A detailed per-run log file:
  - `logs/runs/playwright-match-<account>-<timestamp>-<pid>.log`
- Optional: `failed_entries.xlsx` (saved when some rows cannot be matched automatically)
- Email notification:
  - If failures exist, an email reply includes the `failed_entries.xlsx` attachment.
  - If no failures, a success email is sent.

### 5.3 Sheet-driven “match statement” decision logic

The RAAS+ match-result Excel is read into DataFrames by sheet name.

The current processor routes work primarily by the presence of specific sheets:

- If sheet `1to1 Matches` exists:
  - processed by `process_1to1_matches(...)`
- If sheet `Group Match` exists:
  - processed by `process_group_matches(...)`
  - **special-case within this sheet**: rows whose `Match Type` equals `reverse_ce_gl` are *skipped here* and processed earlier via `process_reverse_ce_gl_matches(...)`

In other words:

- Reverse CE/GL rows are handled first (Step 4.5)
- Then standard 1-to-1 matches (Step 6)
- Then group matches excluding reverse CE/GL (Step 7)

### 5.4 Match types and “reverse_ce_gl”

Within the `Group Match` sheet, the processor uses the `Match Type` column:

- `reverse_ce_gl`:
  - Processed by `process_reverse_ce_gl_matches(...)`, which navigates to **Reconciliation Statements** and reconciles a special two-company-transaction pattern.
  - The implementation expects **exactly 2** `CSGP Reference` values (comma-separated).
- Any other `Match Type` value:
  - Processed by `process_group_matches(...)` as normal group matching.

### 5.5 How a 1-to-1 match is applied (what the automation does)

For each row in `1to1 Matches`:

1. Read:
   - `Bank Reference Number`
   - `CSGP Reference`
2. Clean references (`clean_ref(...)` coerces numeric-like refs to integer-ish string).
3. Filter the main grid by `Ext. Ref. Nbr.` using the bank ref.
4. If no records (or a warning icon is present), the row is tracked as a failure.
5. Otherwise, search the detail area for the CSGP ref and select the match checkbox in the detail grid.

Failures are accumulated into `self.failed_entries` (deduped by bank ref via `self.failed_bank_refs`).

### 5.6 How a group match is applied (1-to-many)

For each row in `Group Match` (non-`reverse_ce_gl` rows):

1. Parse the row:
   - Take the first bank ref from `Bank Reference Number` (comma-separated input is supported).
   - Split `CSGP Reference` into multiple refs.
2. Filter the main grid by bank ref.
3. Enable “Multiple Matching” checkbox (tries two known UI selectors).
4. For each CSGP ref, search and click the match checkbox.

### 5.7 Finalization

After all matching attempts:

- Click **Process** to process matched items in the UI.
- Save failures to `failed_entries.xlsx` (if any).
- Cleanup browser.
- Send pingback + email.
